1. Executive Summary: What We Built and Why

Imagine running a high-precision manufacturing assembly plant producing smartphones or automotive sub-assemblies. You place hundreds of purchase orders every day with independent vendors worldwide.

  • If a shipment arrives on time: Production humming smoothly, customer demand is fulfilled, and capital flows as scheduled.
  • If a shipment is delayed: Entire assembly lines halt, workers sit idle, emergency air freight must be booked at 5× cost, and SLA breach penalties occur.
The Core System Objective: We built an intelligent decision-support system for procurement managers. Before a purchase order is dispatched, our system evaluates parameters known at the moment of order placement and predicts:

🔴 HIGH RISK (LATE DELIVERY) or 🟢 LOW RISK (ON-TIME DELIVERY)

The Two Scratch AI Models

Rather than importing pre-made shortcuts, we coded both models by hand from fundamental linear algebra and probability theory in NumPy:

  • Gaussian Naive Bayes (The Profile Matcher - Generative): Builds two probability profiles (one for historical late shipments and one for on-time shipments) and asks which profile an incoming order fits better.
  • Logistic Regression (The Scorekeeper - Discriminative): Directly calculates a weighted risk score across all clues, maps it through an S-shaped sigmoid function, and computes a calibrated risk percentage (0% to 100%).

2. Business Problem & Procurement Context

The Asymmetric Cost of Machine Learning Errors

In classical machine learning benchmarks, accuracy treats all mistakes equally. In supply chain operations, errors have profoundly asymmetric financial consequences:

Actual: LATE (Class 1) Actual: ON-TIME (Class 0)
Predicted LATE (1) True Positive (TP)
Late shipment caught; buffer stock or backup carrier engaged.		 False Positive (FP)
Safe vendor flagged; minor administrative cost (10-min phone call).
Predicted SAFE (0) False Negative (FN) - CATASTROPHIC
Late shipment missed; factory assembly line halts!		 True Negative (TN)
Smooth normal operations; zero friction.
Key Metric Takeaway: A False Negative is financially devastating, whereas a False Positive is merely inconvenient. Therefore, High-Risk Recall (capturing actual late shipments) is our primary metric, not overall accuracy.
\(\text{Recall} = \frac{\text{True Positives (TP)}}{\text{True Positives (TP)} + \text{False Negatives (FN)}}\)

3. Dataset & Target Leakage Prevention

We trained and evaluated our system using the real-world DataCo Smart Supply Chain Dataset (180,519 rows × 53 columns). The target column is Late_delivery_risk (54.83% Late vs. 45.17% On-Time).

The Anti-Cheating Rule (Target Leakage Safeguard)

During our cloud exploratory data analysis, we identified two severe target leakages that would give a model "fake" 100% accuracy:

  1. Days for shipping (real): Only recorded after the package reaches its destination.
  2. Delivery Status: Explicitly contains the text "Late delivery".

We permanently eliminated both columns, restricting feature inputs strictly to pre-shipment data known at purchase order creation: Days for shipment (scheduled), Shipping Mode, Product Price, Discount Rate, Order Quantity, Profit Ratio, Customer Segment, and Market.

Calculates class priors, feature means, and variances. Adds variance smoothing (\(\epsilon = 10^{-9}\)) to prevent division by zero, and conducts all probability operations in log-space to prevent floating-point underflow.

# Vectorized Log-Likelihood Computation

log_posteriors[:, idx] = log_prior + log_likelihood

# Safe Log-Sum-Exp Normalization

5.3 src/models/logistic_regression.py (Scratch Vectorized Logistic Regression)

Implements vectorized gradient descent, a numerically stable branching sigmoid using np.where, binary cross-entropy loss with \(L_2\) regularization penalty, and early stopping.

# Numerically Stable Branching Sigmoid
def _sigmoid(self, z):
    z = np.clip(z, -500.0, 500.0)
    return np.where(z >= 0, 1.0 / (1.0 + np.exp(-z)), np.exp(z) / (1.0 + np.exp(z)))

# Vectorized Gradient Descent Step
z = np.dot(X, self.weights) + self.bias
y_pred = self._sigmoid(z)
dw = (1.0 / n_samples) * np.dot(X.T, (y_pred - y)) + (self.l2_penalty / n_samples) * self.weights
db = (1.0 / n_samples) * np.sum(y_pred - y)
self.weights -= self.learning_rate * dw
self.bias -= self.learning_rate * db

7. Why Logistic Regression Defeated Naive Bayes

The Scientific Reason: Violation of Feature Independence

Gaussian Naive Bayes relies on the foundational assumption that all features are conditionally independent:

\(P(x_1, x_2, \dots, x_d \mid Y) = \prod_{j=1}^{d} P(x_j \mid Y)\)

In supply chain operations, this assumption completely collapses: Shipping Mode = First Class is heavily correlated with Scheduled Days = 1. Because these features are collinear, Naive Bayes counts the same risk twice, distorting probability distributions and missing ~20% more late deliveries.

In contrast, Logistic Regression is a discriminative model that makes no independence assumptions. It simultaneously balances interrelated weights across features, making it the superior model for real-world procurement risk management.

8. Master Viva & Interview Q&A Cheatsheet

Q1: Why did you build the models from scratch in NumPy instead of just using Scikit-Learn?
"Implementing the algorithms from scratch demonstrates a fundamental grasp of machine learning mathematics—vectorized gradient descent, loss functions, numerical stability safeguards like Log-Sum-Exp, and log-space arithmetic. Scikit-Learn was then used as an objective verification baseline, where our scratch code achieved over 99.2% parity."
Q2: What is the fundamental difference between Generative and Discriminative models?
"A Generative model (like Gaussian Naive Bayes) learns the joint probability \(P(X, Y)\) by modeling how each class generates feature distributions: 'What does a typical on-time order look like vs. a late order?'
A Discriminative model (like Logistic Regression) focuses strictly on the decision boundary \(P(Y \mid X)\), directly separating late and on-time orders without modeling input generation."
Q3: What is Target Leakage and how did you prevent it?
"Target leakage happens when features contain information that would only be available after the target event has taken place. In DataCo, Days for shipping (real) and Delivery Status give away delivery outcomes. Including them creates an artificially perfect model in training that is useless in production. We permanently removed both during EDA."
Q4: Why is High-Risk Recall prioritized over Accuracy?
"In supply chain management, prediction errors have asymmetric costs. Missing a late delivery (False Negative) shuts down factory assembly lines, causing severe financial penalties. Flagging an on-time delivery (False Positive) only results in a routine check-in. Because False Negatives are far more damaging, High-Risk Recall is our north-star metric."
Q5: How does decision threshold tuning benefit a procurement manager?
"Standard binary classifiers use a default threshold of 0.50. In our Streamlit dashboard, a procurement manager can lower the threshold to 0.30. This makes the system more sensitive, increasing late shipment recall from 70.6% to nearly 78%, ensuring almost no delayed orders slip through undetected."
Q6: What techniques did you use for numerical stability in code?
"In Naive Bayes, we operated entirely in log-space to prevent floating-point underflow, added variance smoothing (\(\epsilon = 10^{-9}\)), and applied the Log-Sum-Exp trick. In Logistic Regression, we used an np.where branching sigmoid with np.clip(z, -500, 500) to prevent floating-point overflow in \(\exp(-z)\), and clipped probabilities to \([\epsilon, 1-\epsilon]\) to avoid \(\ln(0)\)."
Q7: How did you divide the work between Person A and Person B?
"Person A led the Discriminative track: derived vectorized cross-entropy, implemented scratch Logistic Regression with \(L_2\) regularization, built the Odds Ratio module, and wrote unit tests.
Person B led the Generative and Systems track: derived Gaussian likelihood with variance smoothing, implemented scratch Naive Bayes with LLR attribution, conducted cloud EDA on Google Colab, and built the Streamlit web dashboard."
